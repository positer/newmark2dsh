# 04 — A run that calls a failing tool, and what ends it

**Owner:** `packages/newmark-core/components/agent-api/`
**Gates:** `scripts/verify-agent-api.mjs` (the checks named in the table below),
`scripts/verify-tool-output-boundary.mjs` (the envelope and the event log cross DSH's
lossless-JSON boundary), `scripts/measure-agent-api-loop-settle-mutations.mjs` (the
falsification harness for those checks).
**Evidence:** `evidence/agent-api-loop-settle/<timestamp>/` — `mutations.json` (the table below,
regenerated by the harness) and `live-measurements.json` (the four live runs, verbatim).

This document exists because the defect it records was **not** what it looked like. The incident
was reported as "a failing tool call loops until the budget is gone", and the obvious reading —
"the failure never reaches the model, so it retries blindly" — is the one that is **false**.

---

## 1. The measurement, before anything was changed (0.2.11, live, `deepseek-flash` on `deepseek-account`)

| # | scenario | outcome |
|---|---|---|
| C | `memory_lab_query "Harness"` — a tool call that **succeeds** | **2 turns**, exit 0, `count=2` |
| F1 | `memory_lab_read` on a component that does not exist, prompt asks in words that the tool not be called again, `max_steps: 3` | **3 of 3 turns called the tool**, ended `max_steps` (exit 4) |
| F2 | the same, asking the model to quote the tool result — `max_steps: 3` | **3 of 3 turns called the tool**, ended `max_steps` |
| L | `memory_lab_update` with an `oldText` that cannot be present — a failure that **throws** | **2 turns**, exit 0, the model quotes the error verbatim |

The fourth row is the control that matters, and it was run on the SAME live bundle, the same
model, the same session, with the same "call no tool again" instruction: a failure the model can
**read** settles in two turns; a failure it cannot read burns the budget. What differs between F1
and L is not whether the failure arrives — it is what the failure says.

## 2. What the model actually receives on a tool failure

Both halves were measured, and they distinguish the two candidates the report named.

**The failure DOES reach the model.** The second request the component hands to `ctx.llm.stream`
carries, in order: the user prompt, the assistant message with the `tool-call` block, and a
`role: 'tool'` message with `isError: true` and `toolCallId` matching the call. Measured by driving
the real `lib/loop.js` and `lib/llm-seam.js` with a fixture model and reading the request
(`scripts/probe-loop-settle.mjs`), and asserted in the gate.

**What it says is the defect.** The whole text of that tool result was `[object Object]`:

```
role=tool  isError=true  toolCallId=c1  [{"type":"text","text":"[object Object]"}]
```

The cause is one expression. `lib/contract.js` classified a tool that reports

```js
{ ok: false, error: { code: 'NOT_FOUND', message: 'Memory component not found: X', details: { selector: 'X' } } }
```

— which is what every MemoryLab tool answers for an absent component — with
`String(value.error || …)`. `String({…})` is exactly `"[object Object]"`. **Measured live, through
the other tool of the same component:**

```
agent_api_tool { tool: "memory_lab_read", arguments: { component: "ZZZ-No-Such-Component-1234" } }
  -> { ok: false, exit: 4, code: "tool_reported_failure", error: "[object Object]" }
```

**A second, independent cause of the same opacity.** The seam normalised a tool call's
`arguments` to an object *in the block itself* — and that block is echoed back to the provider on
the next turn, where DSH's published `ToolCallBlock.arguments` is a **string**
(`dsh-llm/lib/typert.host.js`) and the DeepSeek Messages adapter reads it with
`JSON.parse` (`dsh-llm-deepseek/lib/index.js`, `toolInput`). Given an object, that parse fails and
the adapter sends `input: {}` — so the model was shown every one of its own earlier calls as having
had **no arguments at all**, next to an error that said nothing. A model that sees "I called it with
nothing, and something failed" has a reason to try again; that is a loop generator, and it is not
fixed by making the error text nicer.

A live self-report is *not* evidence here and is recorded as a negative: asked to quote the
arguments of its own previous call, the model answered `{"query":"Harness"}` — correct, and
reconstructible from its own intent, so it does not show what the provider sent. The request shape
above does.

## 3. What was changed

| where | what | why |
|---|---|---|
| `lib/contract.js` | `describeFailure(value)` — message + code + bounded details, never `String(object)`; used by both classifiers and by the tool-error arm | a structured failure reaches the model as `NOT_FOUND: Memory component not found: X {"selector":"X"}` |
| `lib/llm-seam.js` | a tool call's `arguments` stay the JSON **text** the type declares; `toolCallArgumentsChecked` keeps the parse failure instead of erasing it; `toolCallKey` canonicalises a call for the retry bound | the provider echo keeps its arguments; two spellings of one call are one call |
| `lib/llm-seam.js` | a stream that throws **after** delivering its `block-end` chunks no longer discards the turn | the DeepSeek adapter validates tool-call JSON at `message_stop`, after every block is delivered, and throws `MALFORMED_RESPONSE`; that used to turn a completed completion into `run_failed` |
| `component.js` | `prepareArguments` at the tool boundary (the registry's object) | one layer below the message, so the message keeps the wire shape; a malformed argument string becomes a legible tool result |
| `lib/loop.js` | `prepareArguments` inside the try; `tool_execution_start`/`_end` carry the arguments, the turn, the result or the error; `DEFAULT_REPEAT_LIMIT` | the failure is a result, not a throw; a receipt can say why |
| `lib/loop.js` | the retry bound: two identical failures, then a directive, then the identical call is **refused**, then a turn to answer; `repeated-tool-failure` if it is called again | a run that answers about the failure is exit 0; a run that will not stop is not `max_steps` |
| `component.js` | the event log carries bounded payloads; `run: { turns, tool_calls, stop_reason, recovered_turns }` on every failure; `tool_calls` is the run's own | the receipt can say what happened AND how far it got |

The bound is keyed on the tool, the canonical arguments **and the failure text**: a failure that
*changes* is progress and starts the count over, so "change approach" stays available.

## 4. The false checks that were deleted, and the ones that were kept

* **Deleted:** nothing was left in place that could not fail. The scratch probe
  (`scripts/probe-loop-settle.mjs`) is a measurement instrument, not a check, and says so; its
  facts are asserted in the gate.
* **Kept, with a control:** the two-turn success case and the two-turn *failing* case are both
  controls. The failing control is deliberate — a "fix" that stopped every run at the first tool
  failure would end the looping defect and break the component, and mutation `M10` proves that
  control can go red.

## 6. Could this defect explain `(judgement failed, 0 turns)`?

**It could, and it did not.** The line is built by `packages/newmark-core/index.js`:

```js
` (judgement ${judgement.status}${judgement.attempted ? `, ${judgement.turns} turns` : ''})`
```

and `judgement.turns` is read from `envelope.result.turns` — while the envelope contract makes
`result` present **exactly when `exit === 0`**. So for **every** exit-2/exit-4 judgement failure
the printed turn count is `0`, whatever the run did. The "0 turns" is not a measurement of a
zero-turn run; it is a measurement of nothing.

The incident itself is recorded, and it names a different cause:

```
2026-10-01T02:42:02.398Z  where=memorylab/judgement  code=INVALID_TOOL_OUTPUT
  message: tool "agent_api_send" returned invalid output: value is not lossless JSON
  status=failed  exit=null  runCode=INVALID_TOOL_OUTPUT  turns=0  toolCalls=0
  boundMs=300000  elapsedMs=160568
```

`exit: null` means **no envelope came back at all** — that is the 0.2.8 `{ turn: undefined }`
defect this component's own notes describe, not a run that ran out of turns. (It has been fixed
since; the boundary gate's `M1` restores it and goes red.) So:

* the line the user saw is explained by the boundary defect, not by this one;
* this defect **would** produce the same sentence — a judgement whose model calls a memory tool
  that answers `{ ok: false }` would loop to `max_steps`, exit 4, and print `failed, 0 turns`;
* the two are distinguishable only in `errors.jsonl`, which records the **verbatim** code
  (`runCode`) and would say `max_steps` rather than `INVALID_TOOL_OUTPUT`. The panel's sentence
  cannot tell them apart, and that is why every failure envelope now carries
  `run: { turns, tool_calls, stop_reason, recovered_turns }`.

**Bounded claim.** The judgement's own procedure (`memory_lab_tag_review` → decide →
`memory_lab_tag_apply`) fails by **throwing**, and a throw is classified legibly — as the live
control in §1 shows. The `[object Object]` path is the `ok: false` return, which is
`memory_lab_read` on an absent component (measured) and any other tool that reports that way. So
the route from this defect to a judgement failure is: **a judgement run calls `memory_lab_read`
for something that is not there** — plausible (the review's evidence names components and tags a
model may want to look up), available (that tool is in the default run set), and **not observed**.
Whether a judgement recovers from a tool failure is a live acceptance run, and it belongs to the
owner of the rebuild button, not to this document.

## 7. What could not be verified here

* **The fixed loop has not been run against the live provider.** The running application loads
  `newmark2dsh@0.2.11` from the pnpm store (hardlinked, byte-identical to this tree at the time of
  writing), and a running module cannot be swapped without installing the new build and restarting
  DSH. So the after-fix behaviour is measured on the exact request the seam hands the service —
  gate + probe — and not through the live tool. **The acceptance run that matters — does a
  judgement recover — needs that deploy.**
* **The provider's view is read, not observed.** That `toolInput` maps an object argument set to
  `{}` is a reading of `dsh-llm-deepseek/lib/index.js:1530-1537` plus the published type; the
  request the component produces was measured directly, and the model's own self-report was
  discarded as evidence (§2).
* Four live runs were spent (§1). No live gate (`verify-agent-api-live.mjs`) was run: it spends
  real model calls, and this defect did not need them.
